# signalhub: a generic signaling server

A WebSocket server in Go that **introduces two or more parties** so they can set up a direct WebRTC connection. It pairs a device with a browser through a short code (Disney+ / Netflix style) and relays messages between the peers of the same session.

It is **generic**: it knows nothing about video, games or any particular application. Any project can use it (`go-link`, a dialer, a softphone, etc.).

> **A standalone repository.** It has its own `go.mod`, imports no code from other projects and no project imports its code. The only contract between signalhub and its clients is the **protocol** described here.

---

## What it does and what it does NOT do

| ✅ Does | ❌ Does not |
|---|---|
| Generates 9-digit pairing codes | Carry video, audio or application data |
| Registers rooms with a UUID v4 ID and keeps a directory of public rooms (opaque metadata) | Store files |
| Joins connections into a **session** | Read the content of the messages (SDP, ICE, room metadata) |
| Relays opaque messages between peers of the same session | Manage rooms, queues, chat or users |
| Hands out ICE servers (STUN/TURN) with temporary credentials | Persist data |

> 📮 **Analogy:** it is a mail carrier. It checks that the addressee lives at the house (same session), but **never opens the envelopes**.

---

## Concepts

- **Signaling:** before WebRTC peers can connect, they must exchange an *offer* and an *answer* (SDP) plus their possible addresses (ICE candidates). That is the "handshake". This server carries those messages; afterwards the traffic flows directly between the peers.
- **Device Authorization Grant (RFC 8628):** the standard Smart TVs use. The device shows a code and the user types it on a website from another device.
- **Namespace (`app`):** each project identifies itself with an `app` (`"go-link"`, `"other"`). A code from one app cannot be used from another.

## Identifiers

| Identifier | Format | Lifetime | Secret? |
|---|---|---|---|
| `device_id` | UUID sent by the client | Permanent | No: it only identifies |
| Pairing code | 9 digits, shown as `113 134 323` | 10 min, **single use** | Partly |
| `room_id` | UUID v4 (`crypto/rand`), generated by the server | While the room is open, **reusable** | Partly: whoever has it can join (except `invite_only` rooms) |
| Invitation: `invite` | 128 random bits in base64url (22 characters), generated by the server | Until the owner asks for another one or the room closes | **Yes**: it is the key of the link |
| Invitation: code | 9 digits, shown as `113 134 323`, generated by the server | Same as `invite` | Partly: it is short, so it is protected by the `join` rate limit (and the application may ask for a PIN) |
| `session_id` | 128 random bits (32 hex) | While the session owner is connected | **Yes** |
| `peer_id` | 128 random bits (32 hex) | One WebSocket connection | No |

## Protocol (v1)

### Transport

- **Endpoint:** `wss://<host>/ws`
- **Format:** one JSON object per WebSocket message, always with the same shape (the "envelope").
- **Version:** the client states it in the URL: `wss://<host>/ws?v=1`.

### The envelope

```json
{
  "type": "signal",
  "app": "go-link",
  "device_id": "",
  "device_secret": "",
  "code": "",
  "room_id": "",
  "public": false,
  "invite_only": false,
  "invite": "",
  "meta": {},
  "rooms": [],
  "session_id": "",
  "peer_id": "",
  "remote": "",
  "to": "",
  "from": "",
  "ice_servers": [],
  "payload": {},
  "error": ""
}
```

Empty fields are omitted (`omitempty`). `payload` is **opaque JSON**: the server relays it without reading it.

### Message types

| `type` | Direction | Fields | Description |
|---|---|---|---|
| `hello` | server → client | `peer_id`, `ice_servers` | First message. Your identity and the STUN/TURN servers to use. |
| `register` | device → server | `app`, `device_id`, `device_secret` | Asks for a pairing code. `device_secret` (required) is a random secret of the device, 43 base64url characters (32 bytes): it binds the `device_id` to whoever knows it. See [Device identity](#device-identity). |
| `code` | server → device | `code` | Formatted code (`113 134 323`). |
| `claim` | browser → server | `app`, `code` | Redeems the code the user typed. |
| `paired` | server → both | `session_id`, `remote` | Pairing succeeded. `remote` is the `peer_id` of the other side. After `reach`, only the browser receives it. |
| `reach` | browser → server | `app`, `device_id` | Joins, **without a code**, the session of the owner that did `register` with that `device_id`. Used to come back to an already linked device. It proves nothing: see [Reconnecting](#sequence-reconnecting-without-a-code). |
| `reached` | server → owner | `session_id`, `remote` | `remote` joined through `reach`. The owner treats it as **unauthenticated** until the application verifies it. |
| `room_open` | owner → server | `public`, `invite_only`, `meta` | Opens a room in its session. `meta` is opaque JSON (game, name, seats). With `invite_only`, the room only accepts `join` with its invitation (not with the `room_id`). |
| `room_opened` | server → owner | `room_id` | The room's UUID v4. |
| `room_update` | owner → server | `room_id`, `meta` | Updates the directory metadata (free seats, queue). No reply on success. |
| `room_close` | owner → server | `room_id` | Closes the room: it leaves the directory and accepts no more `join`. No reply on success. |
| `invite_create` | owner → server | `room_id` | Creates the room's invitation. If it already had one, it replaces it: the old one stops working. |
| `invite_created` | server → owner | `room_id`, `invite`, `code` | The new invitation: `invite` for the link and the QR code, `code` (9 digits without spaces) to type. |
| `rooms_list` | client → server | `app` | Asks for the directory of **public** rooms of that app. |
| `rooms` | server → client | `rooms` | List `[{room_id, meta}]`, oldest first. Never includes private rooms. When there are no rooms, the `rooms` field is omitted. |
| `join` | guest → server | `app` and one of `room_id`, `invite` or `code` | Joins the session that owns that room. With `invite` or `code` it enters through the invitation; an `invite_only` room refuses the `room_id` with `room not found`. |
| `joined` | server → guest | `session_id`, `remote`, `room_id` | You joined. `remote` is the owner's `peer_id`. |
| `peer_joined` | server → owner | `session_id`, `remote`, `room_id` | A new peer (`remote`) joined through that room. |
| `signal` | peer → server → peer | `to` (sending), `from` (receiving), `payload` | Opaque relay (SDP, ICE, anything). |
| `peer_left` | server → peers | `session_id`, `from` | A peer disconnected. |
| `error` | server → client | `error` | Readable error. |

### Roles in a session

- **Owner:** whoever did `register` (the device). The session is created on the first `register`, even before anyone is linked, so the device can open rooms right away. It can open, update and close rooms.
- A repeated `register` replaces the pending code but keeps the session. The `app` cannot change within the same connection, and each connection owns **a single** `device_id`: registering with another one replaces the previous one.
- **Peers:** whoever did `claim`, `reach` or `join`. A peer belongs to a single session per connection.
- **Star** topology: peers can only send `signal` to the owner, and the owner to anyone in its session. So a guest cannot bother another guest.
- If the **owner** disconnects, the session ends: everyone receives `peer_left` and its rooms are closed and removed from the directory.
- The messages of one connection are handled **in order**. `room_update` and `room_close` have no reply: a client that needs to know they were applied can send any message that does reply afterwards (for example `rooms_list`) and wait for that reply.

### Errors

The `error` field always carries one of these fixed texts, so clients can compare them:

| Text | When |
|---|---|
| `invalid or expired code` | Unknown, expired, already used or another app's code |
| `app not allowed` | Empty `app` or not in `ALLOWED_APPS` |
| `invalid device_id` | `device_id` that is not a UUID, or `device_secret` missing or not 43 base64url characters |
| `device_id taken` | `register` with a `device_id` already bound to another `device_secret` |
| `peer already belongs to a session` | The connection is already part of a session (including a device trying to redeem its own code) |
| `could not allocate a pairing code` | No free code was found (nearly impossible) |
| `not in a session` | `signal` without being in a session |
| `target not allowed` | `signal` to someone outside the session, or from guest to guest |
| `peer not connected` | The target of the `signal` is no longer connected |
| `only the session owner can manage rooms` | `room_*` from a connection that is not the owner |
| `room limit reached` | `MAX_ROOMS_PER_SESSION` exceeded |
| `device not connected` | `reach` to a `device_id` without a connected owner in that `app` |
| `room not found` | Unknown or closed room, another app's or another owner's room, or an `invite_only` room asked for by `room_id` |
| `invalid or expired invite` | `join` with an `invite` or `code` that matches no current invitation of that app (always the same text) |
| `invalid meta` | `meta` that is not valid JSON or is larger than 4 KB |
| `rate limit exceeded` | Too many `claim`/`reach`/`join`, `rooms_list` or `register`/`room_open`/`invite_create` from the same IP |
| `too many messages` | The connection sent more messages per second than allowed; the server closes it |
| `invalid message` / `unsupported message type` | Broken JSON or unknown `type` |

### Sequence: pairing

```
Device                         signalhub                        Browser
  │── connect ───────────────────►│                                 │
  │◄─ hello {peer_id: A} ─────────│                                 │
  │── register {app, device_id} ─►│                                 │
  │◄─ code {"113 134 323"} ───────│                                 │
  │                               │◄──────────────────── connect ───│
  │                               │─── hello {peer_id: B} ─────────►│
  │                               │◄─── claim {app, "113134323"} ───│
  │◄─ paired {S, remote: B} ──────│─── paired {S, remote: A} ──────►│
  │── signal {to: B, offer} ─────►│─── signal {from: A, offer} ────►│
  │◄─ signal {from: B, answer} ───│◄── signal {to: A, answer} ──────│
```

### Sequence: reconnecting without a code

A browser that was already linked with the code can come back to the same device after reloading the page or after the device restarts. signalhub only puts it in the session: **authentication belongs to the application**. In go-link, the device gave the browser a secret over the encrypted DataChannel (DTLS) when they linked, and the browser presents it over that same channel; signalhub never sees it.

```
Device (owner, device_id D)    signalhub                        Browser
  │── register {app, D} ─────────►│                                 │
  │                               │◄──── reach {app, device_id: D} ─│
  │◄─ reached {S, remote: B} ─────│─── paired {S, remote: A} ──────►│
  │── signal {to: B, offer} ─────►│─── signal {from: A, offer} ────►│
  │         (the application verifies the browser over WebRTC)       │
```

- The `device_id → owner` index lives in memory while the owner is connected. If the device reconnects with the same `device_id`, the index points to the new connection.
- If the device is not connected yet (for example, it is restarting), `reach` answers `device not connected` and the browser retries.

### Device identity

Otherwise, anyone who knows a `device_id` could `register` with it and receive the `reach` of that device's browsers. To prevent it, the device sends its own `device_secret` in `register` (32 random bytes in base64url, kept in its configuration):

- The first `register` **binds** the `device_id` to `SHA-256(device_secret)`. While the binding lives, a `register` with the same `device_id` and another secret gets `device_id taken`.
- The binding lives **in memory** for 30 days after that device's last `register`, even if the device disconnects. If signalhub restarts it is lost, and the first one to register binds it again: that is why the application **must not trust signalhub** to know it talks to the real device. In go-link, the device proves itself before the browser presents its token (an HMAC challenge over the encrypted DataChannel).
- A `register` without `device_secret` is refused with `invalid device_id`: every device must send it.

### Sequence: invitation

```
Device (owner S)               signalhub                        Guest
  │── room_open {invite_only} ───►│                                 │
  │◄─ room_opened {room_id: R} ───│                                 │
  │── invite_create {R} ─────────►│                                 │
  │◄─ invite_created {R, T, C} ───│   (link /g/T, QR of that link, code C)
  │                               │◄──── join {app, invite: T} ─────│  (or code: C)
  │◄─ peer_joined {S, P, R} ──────│─── joined {S, remote: A, R} ───►│
  │── invite_create {R} ─────────►│   ("New link": T and C stop working)
```

### Sequence: room and join

```
Device (owner S)               signalhub                        Guest
  │── room_open {public, meta} ──►│                                 │
  │◄─ room_opened {room_id: R} ───│                                 │
  │   (the application shares the link /r/R)                        │
  │                               │◄──── rooms_list {app} ──────────│  (public lobby only)
  │                               │───── rooms [{R, meta}] ────────►│
  │                               │◄──── join {app, room_id: R} ────│
  │◄─ peer_joined {S, C, R} ──────│─── joined {S, remote: A, R} ───►│
  │── signal {to: C, offer} ─────►│─── signal {from: A, offer} ────►│
```

## Rules

| Rule | Value |
|---|---|
| Pairing code TTL | 10 minutes |
| Pairing code uses | 1 (deleted when redeemed) |
| Room lifetime | While the owner is connected and does not `room_close` |
| Rooms per session | 1 by default (`MAX_ROOMS_PER_SESSION`) |
| `meta` size | 4 KB |
| `rooms_list` rate limit | 30 per minute per IP |
| Maximum message size | 64 KB |
| Outgoing buffer per connection | 32 messages (when full, messages are dropped: a slow client never holds back the rest) |
| `claim` / `reach` / `join` rate limit | 5 per minute per IP (they share the counter) |
| Redeem errors | Always the same message (`invalid or expired code`), to give no hints |
| Invitations per room | 1 (`invite_create` replaces the previous one); they die with the room |
| Invitation errors | Always `invalid or expired invite`; `join` by invitation shares the `join` rate limit (5 per minute per IP) |

### Internal design rules

- **Exactly one goroutine writes to each socket** (`writeLoop`). gorilla/websocket does not allow concurrent writes.
- **`deliver()` never blocks:** when the buffer is full, the message is dropped.
- A `done` channel is closed, **never** the `send` channel, to avoid a `panic` from writing to a closed channel.
- **`From` is set by the server**, never copied from the client.
- Notifications are sent **outside** the mutex.
- `TakePairing` reads and deletes **atomically** (single-use redeem).
- The `services` know nothing about WebSockets or the kind of storage: they are tested with a fake repository.

## Configuration (environment variables)

| Variable | Default | Description |
|---|---|---|
| `ADDR` | `:8080` | Listen address |
| `ALLOWED_ORIGINS` | *(empty)* | Allowed web origins, comma separated. Native clients (no `Origin`) are always accepted. |
| `ALLOWED_APPS` | *(empty = all)* | Accepted apps, comma separated |
| `PAIRING_TTL` | `10m` | Lifetime of the 9-digit code |
| `STUN_URLS` | `stun:stun.l.google.com:19302` | STUN servers |
| `TURN_URLS` | *(empty)* | E.g. `turn:turn.example.com:3478?transport=udp` |
| `TURN_SECRET` | *(empty)* | Secret shared with coturn (`static-auth-secret`), at least 32 characters |
| `TURN_TTL` | `12h` | Lifetime of the TURN credentials |
| `RATE_LIMIT_PER_MIN` | `5` | `claim`/`reach`/`join` attempts per IP (IPv6 addresses count by their `/64`) |
| `OWNER_RATE_PER_MIN` | `30` | `register`, `room_open` and `invite_create` per IP |
| `MAX_CONNS_PER_IP` | `20` | Connections open at once from one IP (IPv6: by `/64`) |
| `MAX_CONNS` | `5000` | Connections open at once in total |
| `MSG_RATE_PER_SEC` | `30` | Messages per second of one connection (bursts of twice that); above it, the connection gets `too many messages` and is closed |
| `MAX_ROOMS_PER_SESSION` | `1` | Rooms open at once per session |
| `CLIENT_IP_HEADER` | *(empty)* | Header with the real client IP when a proxy sits in front (`X-Forwarded-For` or `X-Real-IP`). Empty = the connection's IP is used. Without it, behind Caddy or a load balancer everyone shares the proxy's IP and the rate limit would be global. |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |

Example for an app called `go-link`:

```bash
ALLOWED_ORIGINS=https://go-link.org
ALLOWED_APPS=go-link
TURN_URLS=turn:turn.example.com:3478?transport=udp,turns:turn.example.com:5349
TURN_SECRET=change-me
```

### Temporary TURN credentials

To avoid publishing a fixed TURN password, signalhub uses the **TURN REST API** mechanism that coturn supports:

- `username = <expiry_timestamp>:<peer_id>`
- `credential = base64(HMAC-SHA1(TURN_SECRET, username))`

The server computes them and hands them out in `hello.ice_servers`. coturn validates them with the same secret and stops accepting them when they expire.

## Storage

Everything lives **in memory** (`map` + `sync.Mutex`) with a TTL janitor, and it will stay that way: it is a design decision, not a stage.

- signalhub is a single process, with no Redis and no database, meant to serve several projects at once (each with its own `app`).
- Everything is ephemeral: if the server restarts, devices reconnect, ask for a new code and reopen their rooms.
- There are no Prometheus metrics and no resume tokens.
- The `Repository` interface stays because it separates the business rules from storage and keeps the tests simple.

The **live WebSocket connections** live in the `Hub`.

## Security

| Risk | Mitigation |
|---|---|
| Guessing codes | 10⁹ space, 10 min TTL, single use, per-IP rate limit (IPv6 by `/64`), generic error |
| Impersonating a device with its `device_id` | `device_secret`: the `device_id` is bound to its hash; also, the application makes the device prove itself before the browser presents its token |
| Exhausting memory or CPU with connections | Per-IP and total connection caps, a messages-per-second limit, a per-IP limit on `register`/`room_open`/`invite_create`, a single `device_id` per connection |
| Impersonating another peer | `From` is set by the server; `session_id` and `peer_id` have 128 bits from `crypto/rand` |
| Injecting messages into another session | Relaying only happens when sender and receiver are in the same session (and follows the star topology) |
| Other websites opening sockets | `CheckOrigin` with an allow list |
| Huge messages | `SetReadLimit(64 KB)` |
| Slow or hung clients | Dropping buffer + ping/pong with `ReadDeadline` |
| Plain-text traffic | `wss://` only (TLS at the proxy) |
| TURN abuse | Temporary HMAC credentials tied to the `peer_id`; coturn quotas (see `deploy/`) |
| Reaching someone else's device with `reach` | `reach` only adds you to the session: the application gives nothing until the peer proves its secret. `device_id` is a UUID v4 (122 random bits), with a per-IP rate limit |

## Deployment

```
Internet ──► Caddy (TLS, wss://signal.example.com) ──► signalhub :8080
         └─► coturn :3478 UDP/TCP  (STUN/TURN)
```

The server **builds signalhub from this source code** with `docker compose`: no image is published to Docker Hub or any other registry. The `Dockerfile` is multi-stage: the binary has no cgo, so the final image is `scratch` with only the binary and CA certificates, no shell, running as a non-root user.

### What you need

- Any Linux server with Docker and the `docker compose` plugin (1 GB of RAM is enough; add 1 GB of swap to build the image on it).
- A domain name pointing to the server, for example `signal.example.com`.
- SSH access from your computer to the server.

### Ports to open

| Port | Protocol | What for |
|---|---|---|
| 80 | TCP | Let's Encrypt certificate (Caddy) |
| 443 | TCP | Signaling: `wss://signal.example.com/ws` |
| 3478 | UDP and TCP | STUN and TURN (coturn) |
| 49300-49400 | UDP | TURN relay (`TURN_MIN_PORT`-`TURN_MAX_PORT`) |

signalhub itself (`127.0.0.1:8090`) is never opened to the internet: Caddy is its only public entry point.

### Step by step

1. **Point the domain** (`signal.example.com`) to the server's public IP and **open the ports** above in the server's firewall.
2. **First deploy** from your computer, in this repository (it sends the last commit, so commit first):
   ```bash
   make deploy SERVER=root@my-server SSH_KEY=~/.ssh/my-key.pem
   ```
   It copies the code to `/opt/signalhub` on the server, creates `/opt/signalhub/deploy/.env` from `deploy/.env.production.example` **with a random `TURN_SECRET`** (`openssl rand -hex 32`, only the server knows it, file mode 600) and stops, asking you to fill in your values.
3. **Edit `/opt/signalhub/deploy/.env` on the server** with your values:

   | Variable | What to put | Example |
   |---|---|---|
   | `SIGNAL_DOMAIN` | The domain of step 1 | `signal.example.com` |
   | `ACME_EMAIL` | Your email, for Let's Encrypt notices | `you@example.com` |
   | `ALLOWED_ORIGINS` | The websites that will use this server, comma separated | `https://app.example.com` |
   | `ALLOWED_APPS` | The `app` names of your clients (empty accepts any) | `my-app` |
   | `STUN_URLS` | This server's STUN | `stun:signal.example.com:3478` |
   | `TURN_URLS` | This server's TURN | `turn:signal.example.com:3478?transport=udp,turn:signal.example.com:3478?transport=tcp` |
   | `TURN_REALM` | Your domain | `example.com` |
   | `TURN_EXTERNAL_IP` | The server's public IP; if it is behind NAT, `public/private` | `198.51.100.7` or `198.51.100.7/10.0.0.5` |
   | `MAX_ROOMS_PER_SESSION` | Rooms a device may keep open at once | `1` |

   Do not change `TURN_SECRET` (already random) or `CLIENT_IP_HEADER` (`X-Forwarded-For`, set by Caddy). The other variables have sensible defaults, described in [Configuration](#configuration-environment-variables).
4. **Deploy again:**
   ```bash
   make deploy SERVER=root@my-server SSH_KEY=~/.ssh/my-key.pem
   ```
   While `.env` still has example values (`example.com`), it refuses to deploy. With your values, it builds the image on the server and starts signalhub, coturn and Caddy, which gets the TLS certificate by itself and renews it automatically.
5. **Check it:**
   ```bash
   make deploy-health SERVER=root@my-server SSH_KEY=~/.ssh/my-key.pem   # ok
   make deploy-logs SERVER=root@my-server SSH_KEY=~/.ssh/my-key.pem
   ```
   Clients connect to `wss://signal.example.com/ws?v=1`.

**Updating:** commit and run `make deploy` again. The server keeps its `deploy/.env` (and its secret).

**Locally:** `make up` does the same on your computer (signalhub + coturn, no Caddy), creating `deploy/.env` with a random `TURN_SECRET` the first time; clients connect to `ws://127.0.0.1:8090/ws?v=1`. `make help` lists every shortcut, and [deploy/README.md](deploy/README.md) has the details (coturn hardening, moving a server).

Health check: `GET /healthz` → `ok`.

## Tests

- **Unit (`services`):** with a fake repository. Cases: a code redeemed twice, an expired code, another app's code, code collisions, `join` to a closed room, a private room that does not show up in `rooms`.
